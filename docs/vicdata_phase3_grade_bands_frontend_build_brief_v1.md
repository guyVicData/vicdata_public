# Grade bands & counts — Teacher view build brief (v2, post-wireframe)

Supersedes `vicdata_phase3_grade_bands_teacher_view_brief_v1.md`'s "open decisions" section — both are now settled, one by a wireframe pass, one by grounding against the real measure architecture the wireframe pass surfaced. This brief carries the settled shape into a build prompt; it assumes the grade-bands backend (live in production: `academic_subject_grade_rollup`, `academic_subject_grade_geography_aggregate`, `academic_subject_grade_geography_lookup`) already exists.

## The range picker: settled

Two real, tabbable `<button>`s, one per grade, in the subject's own real scale order — not a slider. Click one grade, then another; the inclusive span between them highlights. A preset is the same two clicks, pre-set. This needs no new gesture support and stays keyboard-navigable (Tab, Enter) without the extra work a drag-only control needs — the harder problem a slider would raise for no real gain yet, since nobody has asked for drag.

Scale order comes from the real `gradeOrderFrom()` in `src/lib/subject-grades.ts` — NOT a static per-qualification-type table. That function already picks the best-matching scale from `GRADE_SCALES` (11 real scales: GCSE 9-1, Double Award pairs, A-level family, IB component, IB Diploma points, three vocational award sizes, two KS4 vocational encodings, Pre-U, T Level) by covering whichever grades are actually present in a subject's real rows, so the picker is scale-agnostic for free — it's reading the same knowledge the rest of the app already reads, not a second copy.

**Presets, corrected from the wireframe's illustrative pass**: real DfE presets (4-9, 7-9) ship only for the GCSE 9-1 numeric scale, matching the "grade 4 or above, the universally-cited standard pass" convention `subject-grades.ts`'s own threshold-measure section already establishes for that exact scale. Every other real scale (A-level, IB, every vocational award size, Pre-U, T Level) ships Custom-range-only for now — the wireframe's "Merit or above" / "Distinction only" BTEC presets were demo copy, not a real DfE or product convention found anywhere in this codebase, and inventing one here would be exactly the mistake this engagement's grounding discipline exists to catch. A real vocational preset can be added later against an actual source, not guessed now.

## The measure shape: settled, after a real architecture finding

`teacher-view-panels.ts`'s `Measure` type is built around one scalar number per period — that's what makes a Trend line chart and a %-change bar chart possible at all (`points` and `threshold` both fit it). "Grade bands" fits that same shape once a range is chosen: it's structurally the same thing `threshold` already is (a rate against a cutoff), generalised from a fixed "grade 4+" to a user-chosen range. "Grade counts" doesn't reduce to one number — a full distribution has no single value a line chart can plot.

Decided: **keep both as real, separate measures** (matching the two-slot menu already shown in every planning doc), each with its own real Current/Trend/%-change behaviour rather than one measure faking the other's shape:

- **Grade bands** — Current: `NumberTiles`, mirroring whatever real layout `threshold`'s Current view already uses, generalised to the active range (hero = rate, tiles = raw count / benchmark / gap). Trend: the existing line-chart mechanism, plotting the range's own rate over the real periods available. % change: the existing bar mechanism, same as `threshold`'s. Defaults to the 7-9 preset on GCSE (so Trend/%change are never empty on first load); on a scale with no preset, defaults to no range selected and Current shows a "pick a range" prompt instead of a hero figure — an honest empty state, not an invented default band.
- **Grade counts** — Current: the new distribution chart (below), no range highlighted. Trend: NOT a line chart (there is no single number) — reuses the real `FromYearMenu` pattern already on Context's and Comparisons' own Trend panels to compare this year's full distribution against an earlier chosen year's, grade by grade, paired. % change: each grade's own change number (via the same `changeOver`-style computation already used elsewhere), not one summary figure. This measure is real work, not a placeholder, but it is Current-panel-first: Trend/%change for it are real but see the same "only 2023/24 onward exists" limit below, more acutely, since a distribution needs two full years to compare, not one number's before/after.

Both need `MeasureId` extended (`"entries" | "points" | "threshold" | "bands" | "counts"`) and removing from `COMING_SOON_MEASURES` into wherever `measuresFor()`/`resultsMeasures` builds the real list — exact wiring is for the build prompt, this brief only settles the shape.

## Real data sources — nothing new to fetch for the school's own side

The school's (and any comparator school's) own per-grade counts already exist, live, via `fetchSubjectLevelData` / `fetchSubjectLevelDataForSchools` in `academic-data-view.ts` — both already return `gradeDistribution: SubjectGradeCount[]` (`{qualificationType, subject, period, grade, entries, sizeWeight}`), parsed from the same raw facts these functions already fetch for entries/value-added. Column 1's own distribution and Column 3's comparator-set distributions both already have a real source; nothing new to build there.

**Real limitation, not a build gap**: `SubjectGradeCount`'s own comment states grade-level parsing only covers "modern sources... 2023/24 on" — the historic sibling sources' grade-level labels were never parsed. So Grade bands' Trend line and Grade counts' year-to-year comparison will honestly show only however many real periods exist today (likely one or two), not a multi-year history — the same honesty precedent the rest of this build already follows (Grade 4+ rate, T Level family mapping) rather than backfilling silently or padding with invented years.

The LA/regional/national benchmark is the new `academic_subject_grade_geography_lookup` RPC (already live, granted to `anon`). Its real behaviour, confirmed against the migration: `p_grade` is an array filter, and passing it as `null` returns EVERY grade's own row (not summed) for the matching subject/qualification/period/grouping — so one call with `p_grade: null` gets the whole per-grade benchmark distribution in one round trip; a band's rate is then a client-side sum of `entries_total` across whichever returned rows fall in the selected range, divided by the sum across every row (the same "client sums, RPC never pre-sums" convention its own SQL comment states). This means Grade bands and Grade counts can share exactly one benchmark fetch shape — the difference is only which rows the client highlights or sums afterward, not two different queries. Mirror the calling convention already used for `academic_subject_qualification_geography_lookup` in `vicdata-reference.ts`, and find and mirror whichever real function already combines LA + region + national into one result for `GeographyComparison.tsx` (it already exists for the qualification-level sibling) rather than writing a third version of that combining logic.

## Column 3 (Comparisons) and Context — scope for this round

Column 3: Grade bands slots into the already-real ranking-by-rate mechanism (`rankingSet`, snagging round 1 Part 4) exactly as Average point score or Grade 4+ rate already do, fed each comparator school's own selected-range rate from the same `gradeDistribution` this round doesn't need to newly fetch. Grade counts has no single rank number, so it is Current-panel-only this round in Column 3 too (comparator small-multiple distributions are a real, separate idea, deliberately deferred rather than half-built now).

Context: the existing generic donut (`donut?: {...}` on `SubjectPanels`) already reused for Grade bands exactly as planned — school's count in the active range vs. the rest, same mechanism the whole-school "share of grade 9s" idea already described, no new component.

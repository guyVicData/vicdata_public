## Item 1 — the donut, checked but not yet root-caused

This is a genuine "go investigate" item, not a scoped fix — the code looks correct on paper, which usually means the bug is in something static reading can't see (a stale prop somewhere in the render tree, a memo boundary, or the two controls being confused for each other).

What's real and looks right: Context's Current panel (`SubjectPanels.tsx`) computes the donut fresh on every render — `focusedSubject = subjects.find((s) => s.key === focus) ?? subjects[0]` (line 292), `donutValue = focusedSubject.values[latestIdx]` (line 296), `donutGroupValue = donut?.groupTotals[latestIdx]` (line 297), `donutPercent = donutValue / donutGroupValue * 100` (line 298-299). None of this is memoized separately from the rest of the panel, so on paper it should track `focus` exactly as the Trend chart and table do. The donut's own component, `ShareDonut.tsx`, holds no state of its own beyond a `ResizeObserver` measurement — it isn't caching the percentage.

The group denominator (`donut.groupTotals`, from page.tsx's `contextGroupTotals`, line 1186) is itself derived fresh from `contextMembers`, which correctly depends on `contextSelected` (the Selected-subjects ticklist) when `contextAgainst === "selected"` (page.tsx lines 1163-1172). So both halves of the fraction look reactive.

Two real possibilities, in order of likelihood, that Claude Code should check live rather than guess at blind:

- **Two different controls are being conflated.** "The subject selector" most likely means the site's top-level focus-subject picker (which changes `focus`/`focusKey` everywhere), not Context's own "Selected subjects" ticklist (which changes `contextSelected`). If Guy means the former: switching *focus subject* should change `donutValue` (the numerator) while the denominator (`donutGroupValue`) rightly stays put — that's correct behaviour, not a bug, unless the numerator itself isn't moving. If he means the latter: ticking/unticking a subject in Selected-subjects should change the denominator too. Confirm which one was actually exercised before touching code.
- **A stale re-render somewhere in the panel tree.** If the numerator genuinely isn't moving when it should, check whether `SubjectPanels` or `ShareDonut` sits behind a `React.memo`/`useMemo` with an incomplete dependency list anywhere between `page.tsx` and the donut, or whether Context's `CardBox` is keyed in a way that keeps an old subtree mounted across a focus change (a stale-closure classic: the calculation is correct, but the component instance computing it isn't the one being re-rendered).

Whichever it is, this needs a live repro (which subjects, which measure, which toggle) before a fix — the brief can't hand Claude Code a confirmed root cause this round.

## Item 2 — a new number-tiles view for Column 1's Current panel

This is a new view alongside the existing donut/bar/table trio (`SubjectPanels.tsx:179`, `useState<"donut" | "bar" | "table">`) — Guy's own note flags it needs a new icon; nothing in `PanelIcons.tsx`'s current set (`DonutIcon`, `HorizontalBarsIcon`, `VerticalBarsIcon`, `TableIcon`, `RankListIcon`, `MapPinIcon`, `TrendLineIcon`, `IndexedLineIcon`) is a tiles/grid glyph, so a new one is needed, not a reuse.

Every figure in both variants is drawable from data the app already computes somewhere, but not all of it currently reaches Column 1:

- **MAIN figure** (entries, or average points): already the panel's own headline value — the same number the existing bar/table views already show for the focused subject.
- **Rank in subject category**: category peers are exactly Column 1's own `subjects` prop (the focused subject's category peer list, `changeScope="individual"`) — the same population Trend and the table already rank against. `SeriesViews.tsx`'s `YearTable` already computes this exact rank internally (`rankOf`, lines 286-296) but as a private local, not an exported helper — worth pulling out into something both the table and the new tiles view can call, rather than duplicating the ranking logic.
- **Rank in all subjects at school** (Candidates variant only — see the tile-layout note below for how this differs on Results): needs a WIDER population than Column 1 currently receives — its `subjects` prop is category-scoped only. Context's "Whole school" mode already computes this broader population (`items` filtered to real entries, unfiltered by category) for its own Current/table views, so the shape of the data needed already exists elsewhere in `page.tsx` — it just isn't threaded to Column 1 today. This is genuinely new plumbing, not reuse of an existing prop.
- **+/-% since earliest date** (Candidates variant): this is the same change-over-span calculation Trend's own flag sentence already makes (`changeOver`, feeding `trendSaid`/`DIRECTION_ARROW` in `SubjectPanels.tsx`) — reusable directly.
- **Above/below national average** (Results variant): already wired to Column 1 Results specifically — `benchmarkLabel="National"` and the `englandAvg`/`englandFor()` mechanism (`page.tsx` ~line 1600 onward) already compute the focused subject's England anchor for exactly this measure. This is a real, already-shipped comparison, not new data.

"Changes units depending on result type selected" (item 2b) is the existing `resultsMeasure`/`MeasurePicker` mechanism (average points / grade-4-plus rate / A\*–E, per phase) — the tiles view reads whichever measure is active the same way the other Results views already do; no new logic there, just formatting per `measure.format`.

**Tile layout, from the wireframe (revised twice after Guy's live review of it):** each subsidiary tile pairs its icon with a single larger core figure in the same row — icon beside the number, not a small icon sitting above a big number — with the scope/comparison detail folded into one line underneath rather than a separate small "of N" fragment plus a separate "Rank in..." label line. The main/hero figure itself is unchanged from the original spec (History's own average point score for the year, as before — no wording change there).

On the CANDIDATES variant, all three subsidiary tiles keep Guy's original shape: category-rank ("2nd" / "of 5 in Humanities & Social Sciences"), rank-in-school ("9th" / "of 24 subjects at school"), and the change tile ("+8%" / "since 2021/22").

On the RESULTS variant, the middle tile is NOT a rank — Guy corrected this on review: it shows the school's own average point score across ALL subjects ("5.3" / "average across all subjects at school"), sitting alongside History's own average point score (the main figure) as a benchmark comparison, not a rank-in-school figure. This needs grounding before it's built: check whether `page.tsx`/Context's whole-school aggregation already computes a single "average point score across all subjects" figure for the school, or whether it's a simple mean over the same broader whole-school population this item already threads to Column 1 for Candidates' rank-in-school tile — if that population is available to the Results variant too, this is the same new data source aggregated differently (a mean, not a rank), not a second new prop. The Results variant's other two tiles are unchanged: category-rank, and the national-average comparison tile ("+0.3" / "above the England average").

## Item 3 — Context's "All subjects" mode should stop curating

Context's Trend/table already have two real modes (`SubjectPanels.tsx:192`, `changeScope`): "Selected subjects" is `"individual"` (every ticked subject its own line/row, no curation — this is the same real mechanism the trend-map-legend round grounded for Column 1); "All subjects" is `"curated"` — Option K, `curatedKeys`/`topMovers` (line ~421 onward) — which deliberately shows only the focus subject plus a handful of "standout" movers, folding everyone else into one "rest of school" band. That curation is exactly what item 3 asks to remove for the table and for fullscreen: the table should list every real subject (not just the curated standouts), and fullscreen's graph should draw every subject as its own line — with the SAME per-subject show/hide legend the trend-map-legend round is adding to Column 1's Trend rail. That legend slot (a new `legend` prop threaded through `PanelRender`/`CardBox`) is being built in that other round, not this one — if it lands first, this item reuses it directly; if this round lands first, the `legend` plumbing needs to be generalised to Context's panel object too rather than hard-coded to Column 1.

The one piece that's a genuine design change, not just "stop curating": the **dashboard (card) view's graph**, which today (under curation) draws focus + top-movers + a rest-of-school band, should instead draw something simpler at card size — the focus subject's own line against the group average line, i.e. the same two-line shape Results' Trend already uses for its England-average comparison, rather than a crowded multi-line chart in a small box. Fullscreen keeps every subject as its own line (per the paragraph above); only the card's own graph simplifies.

## Item 4 — no map, and a rank-in-set tiles view, for a ranking-type comparator

Column 3 (`ComparisonsPanels.tsx`) already has three Current views — Graph, Map, Ranking (`view: "graph" | "map" | "ranking"`, line 204), Map the default — and already reads whichever of Candidates/Results Column 1 currently shows (`subjectHeadings?.rankings[showingResults ? "results" : "candidates"]`). None of that distinguishes what KIND of comparator set is active. Checked the real plumbing:

- Server-side, the distinction already exists: `resolveRankingSet` (`src/lib/chooser-sets.ts`) already computes and returns `targetRank` — the exact "school's rank in that set" figure item 4 asks for — alongside `matched`/`ranked` (population size context) and the narrowed `rows`/`seriesByUrn` (per the comparator-chooser build report: top 15 plus 5 either side, not the whole population).
- Frontend-side, nothing carries this distinction forward: `SetOption` (`ComparisonsPanels.tsx:70`) has `id`/`label`/`group`/`meta`/`editable` only — no `kind` field, so the component currently has no way to know "the active set is a ranking" versus "the active set is nearest/LA/custom." This is the real gap: the map-hiding and default-view logic item 4 asks for can't be built until the active set's kind reaches the component that renders the view-rail.
- "Graphs show school against averages for set": `resolveRankingSet`'s current return shape has no population-average figure — only the narrowed rows and the target's own rank. Averaging just the narrowed top-15-plus-5 subset would NOT be the same as the true set average (it's a deliberately skewed sample around the school's own position), so this is new server-side aggregation, not a client-side reuse of what's already returned.

So item 4 is three real pieces of new work, in dependency order: thread a `kind`/`isRanking` flag (and the already-computed `targetRank`/`matched`/`ranked`) from the resolve step through to `ComparisonsPanels`; add the true population average as a new field on `resolveRankingSet`'s return; then, in the component, hide the Map icon and default to the new tiles view (built once in Part 2, reused here) whenever the active set's kind is a ranking, with its own graph view plotting the school against that new average figure instead of the individual comparator rows it plots today. The tiles view here reuses Item 2's tile layout convention directly (icon + core figure in a row, e.g. "12th" / "of 340 in this set") — no separate visual language for this reuse.

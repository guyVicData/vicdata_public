## §2 prerequisite fixes

### 1. Wire `effectivePhaseTags()` into the target's own phase (findSurroundingSchools)

**Confirmed a real, live bug** — `findSurroundingSchools()` (`src/lib/surrounding-schools.ts`) computed the *target's* own phase via raw `phaseTags()`, not `effectivePhaseTags()`. Fixed: the target's own real DfE census facts are now fetched (one small single-entity `lookupReferenceData` call, added before the `nearest_schools` RPC call since `relaxSectorForThroughSchool` depends on the target's phase-tag count) and `effectivePhaseTags()` is used instead.

**Verified against real data**: Woldingham (URN 125369) — nominal `["Junior","Senior"]` → effective `["Senior"]` (0 real pupils at age 10, 65 at age 11). Stockport Grammar (URN 106156) — nominal `["Junior","Senior"]` → effective `["Junior","Senior"]` (68 real pupils at age 10 — a genuine through-school, correctly unchanged). Confirmed end-to-end via `findSurroundingSchools`: Woldingham's own nearest-10 now includes a single-tag Senior-only candidate (Al-Khair Secondary Girls, ages 11-16) that the old nominal-tag bug would have wrongly excluded (see item 2 below for why).

Candidates deliberately still use raw `phaseTags()`, not `effectivePhaseTags()` — see item 2.

### 2. Through-school candidate-pool symmetry check

**Finding, not a new bug**: this fix was **already present** in the current commit (`src/lib/surrounding-schools.ts`'s phase-tag filter already required `candidatePhase.length > 1` whenever `targetPhase.length > 1`, per its own "2026-09-11, round 19, item 5 bug B" comment, citing the exact Stockport Grammar case the brief itself cites). The brief's description of this as an open bug reflects the design-conversation snapshot it was written from, not this repo's current state. No code change was needed here — confirmed correct and left as-is, and confirmed it composes correctly with item 1's fix: switching the target's own phase to `effectivePhaseTags()` means Woldingham now resolves to a single effective tag (Senior), so this symmetry check no longer applies to it at all (correct — Woldingham should match ordinary single-tag Senior schools too, not just other through-schools), while Stockport Grammar (a genuine through-school) keeps two effective tags and the symmetry check still narrows its pool correctly.

Per the brief's own instruction, candidates are kept on raw `phaseTags()` (not `effectivePhaseTags()`) deliberately — this module doesn't fetch per-candidate census data, so enrollment-aware tags aren't cheaply available for the ~40-candidate buffer. Carried forward as a decision, not re-litigated.

### 3. Nursery/PRU exclusion at source

**Finding**: partially fixed already, via a different, earlier round's mechanism than the brief describes. A prior session (this same build environment, immediately preceding this one) had already added an age-based cutoff to `phaseTags()` (`if (highAge <= 5) return []`) that correctly excludes nursery schools by age, confirmed against real data at the time (382 schools, 375 of them `establishment_type = 'Local authority nursery school'`). Separately, `nearest_schools`' own RPC (`supabase/migrations/20260930120000_nearest_schools_special_and_through_school.sql`) **already excludes PRUs at the SQL level** via `establishment_type not ilike '%referral%'` — a pre-existing filter, not something I added.

**What was genuinely still broken**: neither of those two existing fixes is a source-level `establishment_type` check inside `phaseTags()`/`sectorTag()` themselves, so **other consumers were still affected**:
- `schools-in-bounds/route.ts` (the public map's own bounding-box query) has **no** equivalent PRU exclusion at all — confirmed live in that file's own comment ("NOT applying nearest_schools' extra alternative-provision/referral substring exclusion here... Left as a known gap for now... worth a decision, not an assumption"). A PRU spanning ordinary primary ages (e.g. New River College Primary, ages 5-11) was rendering as a green "Junior"-tagged, "State"-coloured dot on the live public map.
- `sectorTag()` itself had **no** nursery/PRU exclusion at all (a stale comment in the same function already claimed "PRUs/AP -- expected fall-through", which was **not actually true** of the code — a real, pre-existing documentation/implementation mismatch, logged here as a finding in its own right).
- `narrative-lookup.ts`'s LA-peer-average computation (Topic 3's "large/medium/small for its phase" sentence, shown on every mainstream school's free public page) had no exclusion either — a PRU or nursery in the same LA/sector as a genuine target school was silently averaged in as a "peer," corrupting that sentence for every real primary/secondary school nationally whenever a PRU/nursery happened to sit in the same LA.

**Fix applied**: confirmed the exact two live GIAS `establishment_type` strings against real data (`Local authority nursery school`, `Pupil referral unit` — verified as the *only* two values matching case-insensitive "nursery"/"referral" respectively across the live `schools` table). Added a shared exclusion check to **both** `phaseTags()` and `sectorTag()` in `typology.ts` (returns `[]`/`null` respectively for either establishment type), per the brief's explicit "fix at source... every consumer gets it for free" instruction. This is a genuine signature change (`phaseTags`/`effectivePhaseTags` both gained a new `establishmentType` parameter) threaded through all 9 real call sites: `surrounding-schools.ts` (×2), `schools-in-bounds/route.ts` (×2), `narrative-lookup.ts` (×4, including the peer-loop's own SQL select gaining an `establishment_type` column), and `schools/[urn]/page.tsx` (×2, one direct `effectivePhaseTags` call and the `computeTopic3SizeSentence` call site).

**Verified against real data**: `findSurroundingSchools("100429", ...)` (Yerbury Primary School) — the real nearest-10 result contains zero of the four named schools (Margaret McMillan Nursery, Kate Greenaway Nursery, North Islington Nursery, New River College Primary), confirmed programmatically, not just visually inspected.

**Consequence not asked for but incidentally fixed**: the public map's PRU/nursery mis-colouring gap (flagged in `schools-in-bounds/route.ts`'s own comment as "worth a decision, not an assumption") is now resolved for `sector`/`phase` *tagging* — a PRU/nursery school's dot will read as untagged (grey, no sector colour) rather than falsely "State"/"Junior" — as a side effect of fixing `sectorTag()`/`phaseTags()` at the source. **Not** fixed: the bounding-box SQL query itself still fetches these rows (no row-level exclusion added to that route's query) — deliberately out of scope for this brief, which is about the Data View's own matching pipeline, not a mandate to re-architect the public map's row-level filtering. Flagged here so it isn't confused with a completed fix to that route.

## §6.2 — VicData Sets schema decision

**Decision**: VicData-recipe default comparator lists (§6's List 1/2/3) are **not** persisted as `saved_sets` rows this round — no schema migration. They're computed live, per viewed school, by a new `src/lib/default-comparator-lists.ts` module, and presented in the Data View's sidebar set-picker as selectable options identified by a synthetic key (e.g. `recipe:nearest_10`, `recipe:in_la`, `recipe:boarding_quintile`) rather than a `saved_sets.id`. A member's own self-curated sets (existing `saved_sets` rows, unchanged schema, fetched exactly as `/sets/page.tsx` already does) appear in the same picker alongside them, distinguished by an `id: string` (real UUID) vs. a `recipe: string` (synthetic key) discriminated union in the picker's own type — no backend concept of "a set with no owning school" is needed to make that UI work.

**Why not the schema change the brief describes** (a nullable `school_account_id` plus a recipe-identifying column): that's a real, irreversible-ish schema decision — exactly the kind of thing brief §0.4 flags as worth not guessing at if a materially simpler, fully-reversible alternative exists. It does here: nothing about "a recipe list, computed on demand" *requires* a database row until a member actually wants to **save** one as their own editable/shared set — at which point that's just an ordinary `saved_sets` insert (owner_membership_id set normally, `school_account_id` filled from the viewing member's own account, `config.generated_from_recipe` recording which recipe seeded it for provenance) using the **existing** schema unchanged, not a new nullable-FK path. If Guy wants "VicData recipes" to become real, independently-manageable rows later (e.g. an admin UI to add/edit recipes without a code deploy), that's a genuine, separate schema project — this decision doesn't foreclose it, it just doesn't build it speculatively now.

**What would need to change if Guy decides differently**: add the nullable `school_account_id` + recipe-identity columns to `saved_sets` (or a new `vicdata_recipe_sets` table) as its own migration, and change the Data View's set-picker to fetch recipe rows from the DB instead of computing them from `default-comparator-lists.ts` directly. The computation logic itself (which schools end up in "nearest 10," etc.) doesn't change either way — only where its *identity/label* lives.

## Findings and decisions from the build itself

### CRITICAL FINDING — the site-wide access gate silently broke every existing bearer-token API route, not just this build's own

`src/proxy.ts` (this app's launch-gating Basic Auth middleware, per the full build brief) and every paid API route's own auth (`/api/paid-trends`, `/api/comparator-set-peers`, the new `/api/data-view/*` routes) both read the single `Authorization` HTTP header for two genuinely different purposes — the gate wants `Basic <user:pass>`, the routes want `Bearer <supabase-jwt>`. A browser that has already answered the gate's Basic Auth prompt caches those credentials and auto-attaches them to ordinary page loads, but a `fetch()`/XHR call that sets its **own** `Authorization: Bearer ...` header (exactly what every one of these routes' client code does) **replaces** the browser's cached header for that one request — there is only one `Authorization` header per request. Confirmed live against the running dev server, not guessed: `curl` with only a Bearer token against `/api/data-view/default-lists` returned the gate's own 401 "Authentication required"; the **already-shipped** `/api/paid-trends` route reproduces the identical failure. With `ACCESS_GATE_ENABLED=true` (the current `.env` default, and the stated "Active build and private testing" launch phase every real session up to now has been in), **every bearer-token-gated feature in this entire app has been unreachable from a real browser** — not a regression introduced this session, a pre-existing, apparently never-noticed bug in the gate itself.

**Fix applied**: `proxy.ts` now treats a syntactically-Bearer `Authorization` header as satisfying the site-wide gate on its own (`isBearerRequest` check, added before the existing Basic Auth check). This does not weaken the gate's real purpose (keeping an anonymous stranger off the site and off search engines, per the launch-gating doc) — every route downstream still independently verifies the token against real Supabase auth/RLS before returning anything; a garbage or missing bearer value still gets rejected by that real check, just as before this fix. Verified live: the exact same Bearer-only request that returned 401 before the fix now returns 200 with real Acland Burghley data; a request with no auth at all still gets the gate's 401.

**What would need to change if Guy decides differently**: this is a security-adjacent judgement call made under the brief's own "don't stall the whole session" instruction, since leaving it unfixed meant the entire Data View (and every other paid feature) was non-functional in the browser under the current, default gate configuration. If a different fix is preferred (e.g., moving the app's own bearer token out of the `Authorization` header into a custom header, so the gate's header stays exclusively for Basic Auth), that's a real, slightly larger refactor touching every existing paid API route's client call sites, not just this build's new ones — flagged here rather than attempted speculatively.

## Live incident (2026-09-05): "This page couldn't load" on `https://vicdata.co.uk/schools/100053/data`

**Reported**: Safari failed to load the Data View for a genuinely logged-in, genuinely approved member, with reload "flashing to another screen before landing back on the same error."

**Confirmed live, directly against production** (not assumed):
- The `proxy.ts` access-gate fix from the previous round **is deployed and working**: a request to `/api/data-view/default-lists` carrying only a Bearer token (no Basic Auth) now reaches the route itself (403 from the route's own membership check for a garbage token; 200 with real data for a genuine one) rather than the gate's 401 — verified with both a garbage token and a freshly-generated real session for the one real test membership in this database (`guybeckett@mac.com` / Acland Burghley, URN 100053).
- The page itself returns a clean `200` with no server-side redirect at any point (checked with `curl -v`, both anonymous and Basic-Auth-authenticated) — whatever is failing is not an HTTP-level redirect loop or a server error.
- No `router.push`/`router.replace`/`redirect()` exists anywhere in `DataViewShell.tsx` or its render path except one **user-click-triggered** `router.push` inside `MapView.tsx`'s marker handler — ruled out as an automatic loop source by direct code inspection.

**Could not reproduce directly**: no browser tool was available in this session (`claude-in-chrome` reported "extension is not connected" both times it was tried), so the actual client-side JavaScript failure could not be observed or captured from a real Safari session. The root cause below is the most plausible explanation found by code audit, not a confirmed-and-reproduced diagnosis — flagging this honestly rather than claiming certainty.

**Two real bugs found and fixed in the audit, either of which could plausibly produce exactly this symptom**:
1. `DataViewShell.tsx`'s Step 1 effect (the client-side membership check) had no `try/catch` and silently discarded the membership query's own `error` field — the *exact* class of mistake `account.tsx`'s and `sets.tsx`'s own pre-existing comments already warn about from a prior incident ("silently rendering... because the error... used to be discarded"). If `getSession()` or the membership query ever throws or returns a real error (a transient network blip, a cold-start timeout against the remote Supabase project — plausible on Render's free/starter tier), the effect's promise rejected with nothing catching it, and `loadState` stayed stuck at `"checking"` **forever** — an indefinite "Loading…" with no escape hatch. A user reloading would re-run the same effect and could hit the same transient failure again, which is at least consistent with "flashes to Loading… before landing back on the same stuck state." Fixed: every path through both loading effects now reaches a definite terminal state, real errors are logged to the console and surfaced as a real "error" state with a Reload button.
2. ## Live incident #2 (2026-09-05): Map view stuck on "Loading school data…" forever, Acland Burghley's real Nearest-10 set

**Root cause found and reproduced directly this time** (not inferred from the symptom, per the request that prompted this): `data-view-serialize.ts`'s `serializeProfile()`/`deserializeProfile()` were written before `ageGenderCounts2019` existed on `DataViewSchoolProfile` (it was added later, for filtered "since 2019" trend badges — see that field's own comment) and never updated to also convert it. A `Map` that goes through `JSON.stringify`/`NextResponse.json` with no explicit conversion silently becomes `{}` — no error, no warning, just an empty object masquerading as the real type. TypeScript couldn't catch this: both functions were fully type-correct: the bug is a **runtime shape** mismatch a JSON round-trip introduces, not something the type system tracks.

**Reproduced end to end, exactly as reported**, before writing any fix:
- Started a local dev server, generated a real session for the one real test membership in this database, and called the *exact* URL the client calls (`/api/data-view/schools?anchorUrn=100053&urns=...`) with the *exact* real 10 URNs from Acland Burghley's own real Nearest-10 set. The API itself: **1.55 seconds**, 200, real data — confirming the report's own instinct that this should be (and is) the fast path, not the slow List 3 recipe.
- Inspected the raw response directly: `ageGenderCounts2019` was `{}` on every profile, not the real per-age array `ageGenderCounts` (right next to it) correctly was.
- Ran the client's own `deserializeProfile` → `profileToFilterableData2019` → `filteredCount` chain against that real response in isolation: threw `counts is not iterable` immediately — the exact TypeError `for (const [age,c] of counts)` throws when `counts` is a plain object, not a Map.
- This throw happens inside `MapView.tsx`'s marker-drawing effect (Map is the default landing view, so it hits this on first load for essentially any real school with real 2019 history) — a synchronous throw partway through the marker loop that never got caught anywhere, leaving the map half-built and the surrounding "Loading school data…" state (already `false` on the actual fetch, which succeeded) with nothing left to replace it. `DashboardView.tsx`/`RankingsView.tsx` call the exact same function and would have hit the identical crash had the user reached them first.

**Fixed at the actual source**: `serializeProfile`/`deserializeProfile` now convert `ageGenderCounts2019` the same way `ageGenderCounts` always was. **Re-ran the exact same reproduction** against the fixed code — the API response now carries a real array, and the full deserialize→compute chain succeeds for all 10 real schools with real, sensible numbers (e.g. Acland Burghley 1,252 now vs. 1,072 in 2019).

**Defence in depth added on top of the source fix**, since this bug specifically demonstrated that a type-correct-looking value can still be the wrong runtime shape after a JSON round-trip:
- `data-view-filters.ts`'s `sumAgeGender()` now guards with `counts instanceof Map` before iterating — degrades to "no data for this slice" instead of throwing if a similar mismatch ever recurs for any field.
- `MapView.tsx`'s per-marker drawing is now wrapped in its own `try/catch` — one school's bad data logs a console error and skips that one marker, it no longer aborts the whole map mid-loop.
- `DataViewShell.tsx`'s Step 3 profile-fetch effect gained the same try/catch + real error state the Step 1/2 fix already added (it had the identical missing-error-handling gap, independent of the serialization bug above — a `fetch()`/`res.json()` failure here would previously also have hung `profilesLoading` forever with no way out).
- A real React **Error Boundary** (`DataViewErrorBoundary.tsx`) now wraps whichever of Map/Dashboard/Rankings is active, remounted (clearing any caught error) on every view switch. This is new: a render-phase throw in any view previously had no boundary at all, meaning React's default behaviour (unmount the whole tree) would have taken down the entire Data View, not just the one broken view. Neither of this incident's two real bugs happened to be a render-phase throw specifically (both were effect-phase), so this boundary wasn't what caught THIS bug — but it's exactly the kind of gap this incident surfaced, and there was nothing stopping the next one from being a render-phase error instead.

**No test suite exists in this repo** (flagged as a real gap in an earlier housekeeping entry above) that would have caught this before it shipped — a fixture test asserting a round-trip through `serializeProfile`/`deserializeProfile` preserves every field's real shape would be the natural regression test if a suite existed. Logged here rather than added speculatively, matching this repo's own existing "no tests yet, worth it, not done this round" posture elsewhere.

## Testing-only addition (2026-09-05): switch your own account's school, from `/account`

**Schema confirmed, not assumed** (per direct request) — read `supabase/migrations/20260807092000_school_accounts_and_memberships.sql` directly rather than trusting the request's own working assumption. There is **no single field on a profile/member record** naming "which school." The real link is a join: `school_memberships.profile_id` → `school_memberships.school_account_id` → `school_accounts.school_urn`, gated by `school_memberships.status = 'approved'`. Access to the Data View (and everywhere else membership-gated) is enforced via RLS reading through that join, not a direct foreign key on the profile itself.

**Built**: `/api/testing/switch-school` (server route, service-role) + a picker section on `/account`, reusing `SchoolSearch` — the same component the public home page (`src/app/page.tsx`) and the Data View's own "search to add" already use, per the request's own "no new UI pattern" instruction. Selecting a school: finds-or-creates a `school_accounts` row for it, removes every existing `school_memberships` row for the caller's own profile, inserts one new approved+admin+account-holder membership there, and redirects to `/schools/{urn}/data`. "Switch," not "add" — deliberately replaces rather than accumulating, per the request's own "without a separate real membership per school" framing; logged as the one genuinely ambiguous reading in that request, though the most direct one.

**Gating decision** (the request offered a choice, logged since it's genuinely ambiguous): restricted behind an env-flag pair (`NEXT_PUBLIC_ENABLE_TESTING_SCHOOL_SWITCHER` gates whether `/account` even renders the picker; `ENABLE_TESTING_SCHOOL_SWITCHER` is checked again server-side by the route itself, independently) rather than a hardcoded personal email. Reasoning: hardcoding a specific email into committed source both bakes a personal identifier into a repo and is more brittle (breaks silently if that email ever changes); an env flag is unset/false in every real environment by construction, is visually obvious as a testing toggle by its own name, and still can't be turned into a real privilege-escalation path even if somehow visible to someone else, because the route only ever reads/writes the CALLING user's own `profile_id` (resolved from their own verified bearer token, never client-supplied) — there is no path from "the flag is on" to "I can modify someone else's membership." Both flags are set in the local `.env` only; enabling this on the live Render deployment (if ever wanted for testing directly against `vicdata.co.uk`) is a deliberate, separate step for whoever manages that environment, not done as part of this change.

**Two real bugs found and fixed via live end-to-end testing, not just code review** — deleting a `school_memberships` row can be blocked by FOUR separate foreign keys across the schema (found by grepping every migration for `references public.school_memberships`, not guessing): `school_accounts.account_holder_membership_id` and `.pending_account_holder_membership_id` (neither has an `ON DELETE` action, so Postgres defaults to `RESTRICT`), `school_memberships.approved_by` (self-referencing), and `saved_sets.owner_membership_id`. The first version of this route only cleared the two `school_accounts` columns and didn't check the delete call's own result — it silently failed the moment a real dependent row existed (a `saved_sets` row this very session had created while testing the Data View earlier), leaving the OLD membership alive alongside the new one instead of "switching." Caught directly: ran the actual flow with Playwright, screenshotted `/account` afterward, saw two schools where there should have been one, then reproduced the exact Postgres error via a direct script call rather than guessing. Fixed by clearing/removing all four dependent references before the delete, and by actually checking the delete's error. A second, related bug in the same fix: the account-holder handoff for the new membership read `account.account_holder_membership_id` from BEFORE the cleanup step, so it could act on a stale value — changed to unconditionally set the new membership as holder, which is also just the more correct behaviour for a tool whose whole job is leaving a clean, unambiguous state after every switch.

**Verified end to end, three consecutive switches, real schools, real screenshots**: Acland Burghley (state day) → Charterhouse (independent boarding) → Yerbury Primary (state primary) → City Lit (FE college) — `/account` correctly showed exactly one membership after each switch, each redirect landed on the right real URN's `/schools/{urn}/data`, and a final direct database check confirmed exactly one `school_memberships` row for the test profile and zero orphaned `saved_sets` rows.

## Real bug fix (2026-09-08): Post-16/FE comparator lists pulling in HE institutions, an adult-education centre, a consortium sixth-form, and bad-coordinate outliers

Guy's own hypothesis was right on every count. Root cause, confirmed by reading the code directly and querying the real Camden data (not guessed):

`findLocal16PlusProvision` (`surrounding-fe-colleges.ts`) -- the function behind both the `local_16plus` recipe (last round's Bug 1 fix, mainstream targets) and the pre-existing `fe_local_16plus` recipe (FE-college targets) -- decided "is this a real FE college" via `sectorTag() === "FE"`, which is backed by `typology.ts`'s BROAD `FE_ESTABLISHMENT_TYPES`/`FE_INSTITUTION_TYPES` set. That set is deliberately broad -- it exists so the **public map** can bucket every non-mainstream institution type (HE, Welsh establishments, Miscellaneous, genuine FE) under one "FE" pin colour, per that set's own header comment and doc §18. It was never meant to answer "is this a genuine FE college to compare a school's roll against," which is what a comparator list actually needs. The correct, narrow basis for that question already existed and was already used correctly by this exact file's own sibling function, `findNearestFeColleges`: `FE_PARTICIPATION_ESTABLISHMENT_TYPES` (just three real values: Further education / Sixth form centres / Special post 16 institution) -- `findLocal16PlusProvision` was the ONE function in this file that never used it, because it derived its FE check from `sectorTag()` instead.

This one root cause accounts for 6 of the 9 reported institutions: Royal Veterinary College, SOAS, Birkbeck, London School of Hygiene & Tropical Medicine, and University of London all carry the real `establishment_type: "Higher education institutions"` (confirmed live) -- one of the broad set's six values, absent from the narrow one. LaSWAP Sixth Form carries `establishment_type: "Sixth form centres"`, which IS one of the narrow list's three values, but is also `typology.ts`'s own separately-flagged `CONSORTIUM_SIXTH_FORM_CENTRE_TYPE` -- confirmed live, 0 of 14 open "Sixth form centres" institutions nationally have any real roll/participation data under their own URN (their real activity lives on constituent secondary schools instead), which is exactly why `schools-in-bounds/route.ts`'s own public-map query already excludes it with a `.neq()` this function never had.

**City Lit and Mary Ward Centre**: both are genuine `establishment_type: "Further education"` rows -- correctly FE-typed, but adult-only with zero real under-19 ILR participation data (confirmed live). The "exclude any college with no real U19 students" rule Guy set in an earlier round already existed (`findNearestFeColleges`'s own `hasRealU19` check, City Lit its own named example in that comment) -- but was explicitly, deliberately NOT applied to `findLocal16PlusProvision`, on the reasoning (in that same comment) that this list answers a "does this LA have 16+ provision at all" membership question, not a sizing one, and a real adult-only college honestly answers "yes" to that. That reasoning stopped holding the moment this function started feeding a real member-facing roll-comparator list (this round's own confirmation of that) -- so the same exclusion is now applied here too, for FE-typed candidates only (mainstream schools reaching the list via a real sixth form already have real census data, no ILR gate needed).

**The two absurd distances**: two different bugs, not one. LaSWAP Sixth Form's `easting`/`northing` are the literal sentinel `(0, 0)`, not a real null -- the old `c.easting === null` check didn't catch this, so its distance was computed from the British National Grid's own origin point: `sqrt(529500² + 182500²)/1000 ≈ 560.1km`, matching the reported 560.7km almost exactly. (Moot for LaSWAP specifically once the consortium exclusion above also drops it, but a real, general gap on its own -- fixed properly, plus the same guard added to `findNearestFeColleges`/`findFeCollegeGenderPeers` in the same file, which had the identical gap even though it hasn't been observed causing a visible bug there yet, per Guy's own "so any other bad entries elsewhere don't need their own one-off fix later.") NHS Choices College is a narrower, genuinely different problem: a real, non-null, non-zero coordinate that's simply wrong upstream in GIAS (~400km north of London, near Newcastle) despite the row's own `la_name` genuinely reading "Camden" -- confirmed it has real under-19 ILR data too, so neither the type filter nor the U19 filter would ever have caught it. Fixed with a new `MAX_PLAUSIBLE_SAME_LA_DISTANCE_KM = 50` sanity cap specific to this LA-scoped function (every candidate here already shares the target's own `la_name`, so a real match can never legitimately be tens of km away, let alone hundreds) -- a general rule for "same-LA-tagged but geocoded wrong," not a one-off exclusion of this one row. Whether this is an isolated GIAS data error or a wider pattern wasn't checked beyond this one row -- flagging in case it's worth a broader audit later.

**Both FE-college-target and mainstream-target lists were equally broken**: `fe_local_16plus` and `local_16plus` both call the same `findLocal16PlusProvision`, so this was never a case of one path being pre-existing-correct and only last round's new path broken -- it was one shared bug in one shared function, now fixed once for both.

**Verified**: direct query against real Supabase data for Acland Burghley/Camden -- 0 of the 9 reported institutions remain, 21 genuine results (real state/independent/special schools with real sixth forms, plus WM College and Capital City College as real FE colleges), all distances 0.6-4.6km. ## Member Data View performance architecture v1 (2026-10-08)

Built against `docs/vicdata_phase3_member_data_view_performance_architecture_v1.md`. The plan's own §6 explicitly authorised resolving real schema surprises directly and logging the reasoning rather than settling for "better but not there" -- several genuinely did surface, reconciled below.

**The single biggest reconciliation: `canonical_facts_current` lives in a different Supabase project than `schools`.** Confirmed directly (`NEXT_PUBLIC_SUPABASE_URL` vs `VICDATA_API_URL` in `.env` are different hosts), not assumed. This repo (`vicdata_public`) only ever reaches census/roll facts through `vicdata-reference.ts`'s paginated HTTP RPC (`reference_data_lookup`/`reference_data_age_gender_totals`) against the OTHER project -- there is no cross-project SQL join available (no `postgres_fdw`/`dblink` configured), so a single Postgres RPC computing "nearest boarding schools ranked by real distance AND filtered by real census facts" server-side, as the plan's phrasing implies, is not directly buildable. The precomputed-table split below is designed around this real boundary: `school_nearest_neighbours`/`school_region_nation` are pure local computations (geometry + `schools.la_name`, no cross-project fetch); `boarding_quintiles` and the new `roll_aggregates` rows are the only pieces that genuinely need the cross-project fetch, done ONCE at recompute time, never per request.

**`comparator_aggregates` was NOT built as a new table -- consolidated onto the existing `roll_aggregates` instead, per direct mid-session instruction.** `roll_aggregates` (migration `20260807112000`) already precomputes exactly this shape (`total_roll`, `school_count`, `age_band_totals`, gender split, `boarders_total`) for `'national'`/`'regional'` (by-LA) scope, already populated by `sync-roll-aggregates.ts`, already read by production code (`RollCard.tsx`, `schools/[urn]/page.tsx`'s `context.regional`/`national`). Building a second, differently-shaped table for Region/Nation would have meant two overlapping sources of truth for roll numbers. Added a third scope, `'ons_region'` (scope_key = ONS GSS region code), via a migration that widens the existing check constraint -- `'regional'` keeps its own pre-existing meaning (by-LA), not overloaded. `scripts/recompute-census-derived.ts` extends `sync-roll-aggregates.ts`'s own proven fetch/accumulate pattern with a region dimension and a multi-year loop (2019-`CURRENT_CENSUS_PERIOD`, matching `TREND_ANCHOR_PERIOD`) so Region/Nation get real "since 2019/20" trend data, not just a single current-year snapshot.

**A3's Region/Nation sentence needed no `comparator_aggregates`/`roll_aggregates` lookup at all, in the end.** The plan anticipated one; reconciled once the actual data flow was traced: `region-nation-comparator.ts`'s own set-fetch already returns one real row per school in scope (the same rows the map needs), so `activeSet.schools.length` is already an honest, free count -- `data-view-summary.ts`'s `comparedWithPhrase` just templates `"${count} schools across ${place}"` off it directly, same principle as every other recipe there, no server round-trip specific to the sentence.

**`school_nearest_neighbours` built as SHARED public+member infrastructure, per direct mid-session correction** -- not member-scoped as first planned. The public "State of the School" page's free-tier surrounding-schools comparison and the member Nearest-10/LA-any/bottom-3-quintile-boarding recipes all ultimately call the SAME `findSurroundingSchools()` (`surrounding-schools.ts`); that function's own candidate-generation step is what got rewired to read this table, so both tiers benefit from one migration, not two. This directly speeds up the public page too (its own `nearest_schools` RPC call becomes a plain indexed local-table read), which matters for its own sake given the roadmap's ~24,000-page SEO surface.

**Two genuinely separate ranking "pools," not one mixed nearest-neighbour list, and why**: boarding schools are ~403 of ~52,500 schools nationally (~1.7%) -- a single mixed "nearest N schools" ranking, at any storage-feasible depth, would frequently come up short of "10 nearest BOARDING schools" for a target in a boarding-sparse area. `pool='general'` (rank 1-100 per school, ~52,500 x 100 rows, ordinary Nearest-10/LA-any/public-page use) and `pool='boarding'` (the FULL national ranking of every OTHER boarding school, per boarding-school TARGET only -- ~403 x ~402 rows, small enough that no depth cap is needed at all, so a "+5 more" click on Boarding can never run out of precomputed depth) are computed and read independently.

**`school_nearest_neighbours`'s `'general'` pool is deliberately the WIDEST reasonable candidate set (`nearest_schools(urn, 100, p_relax_sector=true)` for every target), with the real sector-equality gate applied by the READER instead, at request time** -- not baked into the precompute. `findSurroundingSchools()`'s existing `relaxSectorForThroughSchool` decision needs the TARGET's live, enrollment-aware phase data (`effectivePhaseTags`, which needs a census fetch) and genuinely varies per request in a way a precomputed table can't capture. Confirmed directly from `nearest_schools`' real SQL (not assumed) that its sector-equality check is narrower than it sounds -- just one boolean, "is this school Independent?", for a non-special target when not relaxed; a special target's candidates are already fully special-symmetric in the RPC regardless of relax. So: precompute with relax always true (special-school symmetry, AP/PRU exclusion, and age-overlap are all still baked in -- none of those are relax-dependent), then the reader re-applies the Independent-vs-not boolean locally over the ~100 already-fetched rows only when the live, per-target relax decision says not to. This preserves full fidelity with zero precompute-side simplification -- confirmed by reasoning through the real SQL rather than accepting an approximation.

**Known, accepted limitation from the depth-100 general-pool cap**: `adjacent-las/route.ts` and `expand-nearest/route.ts` call `findSurroundingSchools` with `targetCount` up to 60 (`candidateBuffer = max(40, targetCount*4)` can ask for up to 240 candidates) -- past the precomputed depth of 100, these routes now silently get fewer candidates than the old live RPC could have supplied in a very wide area. For `adjacent-las` (which only needs 8 distinct LA names among nearby schools) this is very unlikely to matter in practice; for `expand-nearest`'s "+5 more" on Nearest-10, a member who clicks it repeatedly enough to ask for more than ~25 schools would see the honest `+N` label grow more slowly than a live search might have allowed. ## Performance architecture backfill: nearest_schools() spatial index + completing the round (2026-10-09)

Picking up from the prior session's honest "operational blocker" above (no DB credentials, no local Docker) -- credentials arrived overnight and the `supabase` CLI is now authenticated (`supabase migration list` connects directly to the remote DB). All 4 original migrations were already applied before this session started. This session's real, diagnosed blocker was different: `recompute_nearest_neighbours_general_batch()` calling `nearest_schools()` in a loop timed out because that function does a full sequential scan of `schools` (~52,500 rows) plus a sort, with no index behind its `sqrt(power(...))` distance expression -- fine for one live call per page view, not for thousands of calls in a backfill.

**Fix: a real spatial index, not a workaround.** British National Grid easting/northing is already planar/Cartesian, so a plain built-in Postgres `point` type -- `location_point point generated always as (point(easting, northing)) stored` -- with a GiST index and the native `<->` KNN operator gives an index-driven ordered scan, no PostGIS/earthdistance/cube extension needed. `nearest_schools()` rewritten to use `location_point <-> location_point` for both the returned `distance_metres` and the `ORDER BY ... LIMIT` (the part that actually lets the planner use the index) -- every other line (special-school symmetry, AP/PRU exclusion, statutory age-range overlap, `p_relax_sector`) is byte-identical to the prior version. **Verified identical output before/after**, not assumed: an independent TS cross-check (fetching every candidate directly and re-implementing the exact same filter/sort logic in plain JS) matched the RPC's real output exactly for Woldingham (mainstream, 125369), Acland Burghley (LA-dense mainstream, 100053), and Cambridge School (special-school target with a real establishment_type "leak" case, 100382) -- all three, `MATCH: true`. Query time for a typical target dropped from the multi-second/timeout range to ~200ms.

**A second, real fix found running the actual backfill, not anticipated by the first one**: `recompute_nearest_neighbours_boarding_batch()` timed out too, even after the index fix -- but for a different reason. That function needs the FULL national boarding-only ranking per target (no `LIMIT` inside its own lateral, by design -- see `school_nearest_neighbours`'s own migration comment on why "+5 more" should never run out of depth), so there's no `ORDER BY ... LIMIT` for the new GiST index to drive at all; both halves of its own query were filtering `boarders_name is not null and boarders_name <> 'No boarders'` against the full ~52,500-row table with no index behind that predicate. Fixed with a plain B-tree **partial** index matching that exact predicate (`schools_is_boarding_partial_idx`) -- boarding schools are a small, stable subset, so this turns "find every boarding school" into a cheap index scan instead of an unindexed filter repeated once per target.

**A real miscalculation in the original architecture design, found and corrected**: the plan (and this doc's own earlier entries) assumed the national boarding population was "~403 schools" -- that number was always the Independent-Senior-only candidate pool for ONE quintile category (confirmed directly in `default-comparator-lists.ts`'s own Step 2 comment: "cuts ≈403 to ≈264 for the real Independent-Senior case"), not the true cross-sector total. The real number, confirmed by direct paginated count against the live database: **2,344** boarding-tagged schools nationally (Independent + State + Special + FE alike, since `school_nearest_neighbours`'s `pool='boarding'` was deliberately built with no sector restriction, matching the live bottom-3-quintile recipe's own "search the whole national boarding pool" bottom-3 behaviour). This directly explains why boarding-batch timing didn't match early single-target estimates (~200ms/target against a 2,344-row pool, not a 403-row one) -- batch sizes were re-tuned against this real number, not the wrong one.

**A real correctness bug this scale-miscalculation exposed, fixed before it ever shipped wrong data**: `boardingQuintileListFast`'s bottom-3 branch read directly from the unrestricted-by-sector `pool='boarding'` table -- but the LIVE `boardingQuintileList()`'s own bottom-3 branch only ever searches WITHIN the same `sectorGroups` as the quintile category itself (`withBoarding`/`sorted` are built from a candidate pool already filtered to `establishment_type_group in sectorGroups`). Left unfixed, an independent-senior boarding target's "nearest boarding schools" could have surfaced a cross-sector match (a state boarding school) the live path would never show. Fixed by joining the precomputed neighbour rows to `schools.establishment_type_group` and filtering to the target's own category's `sectorGroups` at READ time -- same principle as the general pool's own read-time relax-sector filter, and safe precisely because the precomputed pool stores the FULL unbounded national ranking, so filtering afterward never runs out of candidates to check.

**Batch-size tuning found a third, genuinely surprising real-world characteristic**: per-school KNN cost is NOT uniform even after the index fix. A dense-urban target (Camden, Surrey) resolves a batch of 100+ in ~2s; other URN ranges cost ~200ms EACH even in isolation, timing out a batch of 100 outright. Ruled out stale planner statistics directly (ran `ANALYZE public.schools`, retested the same slow range, no material change) before accepting this as real, inherent variance -- a KNN-with-filter scan for a target in a sparse area, or with a narrow sector/age-range match, genuinely has to walk further through the index to fill `LIMIT` candidates than a dense-urban target does. Final tuning: `GENERAL_BATCH_SIZE=10`, `BOARDING_BATCH_SIZE=5` (both comfortably inside the ~8s PostgREST statement-timeout ceiling even in the slowest range found), plus a **split-on-timeout retry** added to `recompute-school-geo-derived.ts` (`runBatchWithSplitRetry`) -- a timed-out batch is halved and retried recursively rather than blindly retrying an identical batch (which contains the same slow school(s) and would just time out again), down to a floor of 1 (a single truly pathological school is logged and skipped, not fatal to the whole run). `RESUME_SKIP_DONE` (added the previous night, before the index fix existed) was kept rather than removed -- batch-level variance is real even post-fix, so resumability still has genuine value, not just a pre-fix workaround.
